# 0031. A pointer array and three scalar DATA owners

Status: Accepted
Date: 2026-10-25

## Context

The initialized overlay 101 prefix was reconstructed as one containing
aggregate. Its game consumers use pointer cells and independently addressed
signed counters; no whole-object consumer requires that aggregate. A natural
member-access cleanup changed nonrelocated instructions. A separate stock
experiment with one genuine pointer array and three initialized signed scalars
preserved the complete allocation and all original pointer relocations. A
scalar-only consumer spelling independently preserved every instruction and
relocation except the intended import names. These are reconstruction choices,
not recovered original declarations or new matching credit.

## Decision

Add only the explicit `pointer-array-three-s32-v1` owner profile with the
existing ordered writable LOCAL provider group. Initially select the reviewed
overlay 101 input. Selection is not proof. Preserve ADR 0023's one-aggregate
default and every ADR 0028/0029 mixed-provider/two-object rule and refusal.

Authenticate the actual configured compiler vector, wrapper frontend and
IDO preprocessed input under the existing single capture deadline. Reuse the
pinned effective-C parser. Require one mutable unsigned-byte pointer array
with a positive literal effective bound and a complete named-base initializer
list, followed by exactly three independently initialized signed-long-o32
zero scalars. Each initializer must resolve one unique compatible effective
extern mutable unsigned-byte-array declaration. Reject shadows, incompatible
redeclarations, pointer variables, functions, qualifiers, unsupported types,
expressions and extra definitions. Source review remains necessary; audit JSON
is never loadable proof authority.

Join those facts to four unique positive GLOBAL OBJECT definitions in the
original compiler DATA. They must cover the complete input adjacently, without
gaps, overlap, suffix, additional allocated definitions, COMMON or assembly.
Every pointer cell has exactly one original ordered aligned zero-addend R32
to a true undefined GLOBAL OBJECT base; the three scalar objects have none.
Keep original symbol indices, sizes, payload and records unchanged. Neither
names containing coordinates nor an arbitrary four-object count establish
identity. An immutable internal capture/witness binds loaded bytes and parsed
symbol/section/index surfaces, and rejects late metadata changes.

Reuse the actual complete writable provider inputs in declared order and the
existing base-only rules for zero-sized character definitions. Ordinary GNU
ld derives group offsets and linked payload. Authenticate each source owner
against its unique real final definition inside the unique whole input map.
Derive all outgoing identities before comparing the entire runtime set and
whole configured replay, including scalar bytes. NULL/lost or swapped source
records must refuse even when configured bytes are identical. No fake root,
field alias, padding object, numeric binding or word modification is allowed.

Keep original compiler output, ordinary link and metadata-only container
conversion separate. Reuse existing source/header/parser/tool/recipe/provider
holds, loaded-byte joins, atomic inventory and Resolver epoch invalidation.
Recheck through end-pack and marker-last publication. A failed validation must
expose no stale authority; restoration permits only a fresh complete retry.
Private capture paths remain holds, not volatile Make dependencies. Existing
capture budgets and strict retail raw-equality guards remain unchanged.

## Consequences

Only actual source/function/module/runtime/ROM and normal-gate acceptance may
retire borrowing. No physical/executable credit follows from this profile.
Other aliases, incompatible pointer views, script/API/lifetime, original object
boundaries, source-only image and native closure remain independent work. Any
reuse needs its own reviewed source/module proof; no general storage-shape
registry or additional provider class is introduced.
