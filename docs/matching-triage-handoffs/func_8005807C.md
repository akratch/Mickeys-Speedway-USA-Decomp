## Resolved 2026-09-11 (lane/p9-oneoff): the carve was wrong, not the body

The closure above is correct about the body and wrong about the residual. The
two-instruction "unreferenced duplicate-return tail" is not a tail of this
function at all -- it is a separate empty function at `0x800580E8`, and splat
folded it into this span because nothing in the image references it.

Measurements, in the order that settled it:

1. `tools/align_symbol.py func_8005807C` reports 27 byte-exact, 0 naming, 2
   structural, displacement tax 0, and `target has instructions the candidate
   does not: +0x64  2 word(s)`. Over the first 27 words the candidate is
   *raw*-identical to the target, not merely masked-identical, and all 16
   relocation offsets, types and identities already agreed.
2. Seven source-equivalent exit spellings -- baseline, leading early `return`,
   trailing `return`, both, `goto` to a tail label, `while`/`break`, and
   `do {} while (0)` -- all emit exactly 27 instructions under configured IDO.
   A dead epilogue is therefore not reachable from any return spelling, which
   is what the previous closure proposed as the next mechanism.
3. The eight bytes are a `jr $ra` + `nop` pair. Genuine inter-object padding in
   this same region is zero-filled: the eight bytes after `osFlashReadArray`,
   at `0x80058008`, are zero. So these eight are code, not fill.
4. Nothing in the 32 MB image references `0x800580E8`: no stored pointer word,
   no `jal`, no `j`. That is why splat had no boundary to cut on, and it is
   also why the stub is unnamed -- it is a dead entry point of this TU, the
   same shape as `func_80028F3C` and the `camlight` family.

`func_800580E8` is declared in `symbol_addrs.us.txt` (tier D, boundary), the
empty stub is written into `src/main/flash_58C10.c` after this function, and
the assembly fallback is removed. `gmake verify` prints the expected SHA1.

The transferable finding: **a small `size_delta` whose residual is a clean
